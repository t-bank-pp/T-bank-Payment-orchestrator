# Как проверить проект

Откройте вкладку **Actions → Payment checks** и выберите последний запуск для ветки `main`. Убедитесь, что коммит запуска совпадает с текущим коммитом `main`. Зелёный статус означает, что прошли проверки кода, миграций и все группы тестов. В Summary находится таблица результатов; в Artifacts — `qa-results` с JUnit XML и полными логами каждой группы.

## Группы проверок

| Группа | Что проверяется |
|---|---|
| 01 · Контракты | Форматы команд и результатов, обязательные поля и версии сообщений |
| 02 · Payment | Приём платежа, идемпотентность, состояния и работа с БД |
| 03 · Executor | Выполнение попыток, блокировка конкурентного исполнения и восстановление lease |
| 04 · Доставка | Kafka, inbox/outbox, повторы сообщений и восстановление после ошибок |
| 05 · Подтверждение | Неоднозначные результаты, сверка, подписанные callback, порядок версий |
| 06 · Каналы | Поведение каналов A/B/C и сквозная обработка результата |

Список файлов распределяется автоматически в `scripts/qa_groups.py`: каждый тестовый файл входит ровно в одну группу. Проверки запускаются последовательно на изолированном CI-стенде с PostgreSQL и Kafka. Пропущенные тесты, пустая группа и отсутствие отчёта считаются ошибкой приёмки. После падения одной группы остальные продолжают выполняться, чтобы отчёт показывал весь результат.

## Повторный запуск

Workflow запускается при push и pull request. Для ручного запуска: **Actions → Payment checks → Run workflow → main**. Зависимости закреплены в `requirements-dev.lock`, версии инфраструктуры и переменные окружения указаны в `.github/workflows/ci.yml`.

Для локального воспроизведения подготовьте PostgreSQL и Kafka, установите зависимости и примените миграции по шагам workflow. Из корня репозитория выполните `python scripts/run_test_group.py <группа>` (contracts, payment, execution, delivery, reconciliation или channels). После всех шести групп выполните `python scripts/qa_summary.py`. Отчёты появятся в `reports/`. Не используйте для тестов БД с нужными данными; интеграционные тесты создают и очищают тестовое окружение.

## Границы результата

Это проверка виртуального платёжного оркестратора: реальные деньги и платёжные системы не подключены. Успешные тесты подтверждают реализованные сценарии, но не заменяют нагрузочное тестирование и проверку будущих стратегий маршрутизации. Исторические ручные прогоны относятся к указанным в них коммитам; актуальный результат всегда проверяется по запуску Actions на `main`.
